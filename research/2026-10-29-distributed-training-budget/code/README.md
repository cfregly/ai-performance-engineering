# A small distributed training budget workbook

Run with Python 3.10 or later; no packages, credentials, model download or GPU are needed.

```sh
python3 -m unittest discover -s code -p 'test_*.py' -v
python3 code/system_budget.py --output evidence/system-budget.json
python3 code/reader_summary.py --output evidence/reader-summary.json
```

Run these commands from the package directory. The workbook counts a hypothetical design. It does not run distributed training, validate model quality, benchmark a kernel, predict a step time or demonstrate a speedup.

The example has 64 generic GPUs, eight nodes and two racks. Two data replicas each have four pipeline stages, each stage on one eight-GPU node. Twelve blocks use hidden width 2048, 16 query heads, two K/V heads, head dimension 128, and 16 top-2 experts. Each expert is a two-matrix 2048→4096→2048 GELU MLP, with no bias or shared expert. The sequence is 2048 tokens and each replica processes eight microbatches per step. Input embedding and output head are untied, with vocabulary 32768. There are two RMSNorms per block and one final RMSNorm. There is no dropout, activation matrix recomputation, auxiliary routing loss, positional-embedding parameter, or checkpoint I/O in the model. A causal positional transformation can be applied without trainable parameters; its scalar operations are outside the dense-GEMM work count.

Attention uses TP4×CP2 on the eight stage ranks. The MoE uses EP8 on those same ranks. This is a change of tensor layout, not a multiplication of the GPU count. In this chosen head-sharded policy, TP ranks 0/1 share K/V head 0 and ranks 2/3 share K/V head 1. Their gradient contributions are summed before the whole K/V matrix is updated. The code explicitly counts unique token selection, a nonidentity reshard, the return shuffle and token reconstruction. Expert work is performed once per selected token/expert pair.

The policy uses whole-matrix Muon for Q/K/V/O and the two matrices of each expert. Embeddings, output head, routers and RMSNorm gains use AdamW. Muon has FP32 master weights, FP32 gradients, one FP32 momentum and a BF16 model copy; AdamW adds a second FP32 moment. Attention matrices gather gradient/master/momentum to a canonical stage rank for five finite Newton–Schulz iterations, then scatter and publish weights and optimizer state. Expert matrices already reside whole on their owners. This canonical owner is an explicit imbalance and communication cost; a distributed equivalent could change the budget, but is not modeled here. The declared FP32 recurrence departs from the pinned Muon reference's BF16 Newton–Schulz input/iteration. It is an approximate transform, not an exact polar/SVD operation or a claim about every Muon implementation.

Each token's loss is normalized by the global 32768-token step count before gradient accumulation. The primary plan chooses full DP allreduce completion after local CP/TP sums, then replica 0 contributes every unique Muon/AdamW norm term while replica 1 contributes zero. One global L2 norm covers all unique gradients; clipping alone does not require this full-allreduce schedule. Duplicate TP/CP/DP copies do not add norm terms. Both optimizers use the same clipping scalar. Updated weights become available to the next step only after the complete optimizer/publication barrier.

Traffic is logical payload bytes sent, each directed transfer counted once. It includes metadata, count exchange, complete vocabulary projection, boundary reconstruction, gradient replication, optimizer gathering/scattering and state publication. It excludes transport headers, padding, retry traffic and physical switch-hop expansion. BF16 activation/activation-gradient transfers and FP32 parameter-gradient transfers are explicit hypothetical precision choices; the workbook does not establish numerical equivalence to a training reference. Endpoint service assumptions are full duplex. The assumed intra-node fabric has no additional shared bottleneck beyond the declared per-GPU capacity. Rack capacities refer to aggregate injected payload, not the sum of every internal switch link traversal.

The traffic table compares two placements of the same work. Placement A keeps each data replica inside one rack; every DP pair crosses racks. Placement B puts stages 0/1 of both replicas in rack 0 and stages 2/3 in rack 1; DP pairs stay within a rack and one pipeline boundary crosses racks. B reduces cross-rack gradient pressure while leaving node NIC traffic and optimizer work. Whether that improves a real step depends on contention, collectives, service rates and overlap.

Resource screens divide declared work or bytes by assumed capacities. In the primary declared full-allreduce-before-norm plan, all training and gradient/PP traffic complete before clipping; optimizer work and publication follow it. This phase assignment follows the chosen DP schedule and replica 0 norm ownership, not clipping alone. The workbook partitions every traffic category into pre-clipping, clipping-barrier or post-clipping ledgers. It grants arbitrary overlap by taking a maximum within each phase, then adds pre- and post-clipping maxima across the global barrier. Norm-scalar service is omitted from that ordered sum and retained in full-step payload screens. It never adds overlapping node/rack/GPU screens within a phase. These necessary floors are 240.6293086208 ms for A and 158.9342814208 ms for B: both exceed the unchanged 150 ms budget for the declared DP schedule AND FP32 single-owner attention Muon policy. They are not runtime estimates. Dense-GEMM counts exclude normalization, activation, softmax, AdamW scalar work, communication kernels and software overhead. Muon FLOPs stay separate from training FLOPs and cannot be added to an MFU numerator. At this teaching-scale 32768-token update the FP32 Muon work is large relative to training work; larger token budgets can change that balance.

The 1F1B diagram assumes equal forward/backward unit service and zero handoff time. Its 22 slots and 4/3/2/1 maximum live microbatches are a dependency illustration. Six idle slots are 27.27% of 22 elapsed slots or 37.5% of 16 busy slots; these use different denominators. The actual model's output head makes stage 3's dense training work about 46.34% larger than the other stages; causal attention also makes later-CP ranks about 9.08% heavier within stages 0–2. Unit slots are not milliseconds and are not calibrated from the resource screens.

The capacity ledger sums all declared retained tensors and active workspaces, including model/master/gradient/moment states, the head's logits and dlogits, communication buckets, whole-matrix optimizer scratch, and live 1F1B activations. GELU's output can be recomputed from its retained preactivation in backward; this is a pointwise operation, not a matrix recomputation. Two routing cases are shown. Streaming 128-token chunks bounds transient expert staging; it does not remove retained backward activations, and skew can require more serial work on one owner. No token is dropped. Framework contexts, allocator reserve/fragmentation, additional vendor-library workspaces, transport buffers, graph pools, compilation and checkpoint buffers remain excluded. Consequently, the ledger is conditional and does not prove that a real implementation fits an 80 GB device.

The independent attention companion has a different MQA workload: sequence 4096, 16 query heads, one K/V head and 128-token tiles. Its optional TP4×CP2 mapping is included only to show why a one-device scratch bound cannot be copied to a distributed step without mapping producer ownership and reductions. It does not calibrate the main model's attention implementation or step time.

The separate analytical reduce-scatter-first alternative splits every DP directed payload into equal pre-norm reduce-scatter and post-clip allgather transfers. Both replicas contribute disjoint reduced-gradient norm terms, with 1,734,566,912 unique parameter elements each. Total bytes, scalar path and mathematical norm/update semantics stay the same. The alternative floors are A 173.4566912 ms and B 113.8923102208 ms. Norm-scalar service is omitted from all alternative screens. A post-phase maximum grants optimistic allgather/optimizer overlap; consumed-gradient dependencies in an actual whole-matrix schedule can raise it. At 150 ms, A is excluded and B is merely not ruled out. This does not replace the primary plan or establish feasibility/runtime/speedup.
