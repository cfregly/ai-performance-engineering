# ZeRO harness completion scope — independent source review

The four ZeRO factories need a real child-training verification path before this part of the goal is complete. The current refusal is a necessary mitigation of false correctness evidence, not a functional replacement. The two original findings do not by themselves require immediately implementing 61 distinct workload verifiers; they do require restoring the affected ZeRO benchmark pair instead of leaving it permanently unavailable.

This review reads the original findings, intake revision `b57e4c6a9e261c09ac09208705d040c81b03d35e`, current source, plan acceptance and retained receipts. It runs no repository code, tests, training, GPU job, install or remote operation. `factory-inventory.json` accounts for all 61 factories by original source and arguments; `source-evidence.json` binds the observed source epoch. Original evidence remains unchanged.

## What was already unavailable before withdrawal

The distinction is between a child that cannot execute its declared configuration and a child that had never been validly verified. All 61 had the latter problem through the shared parent surrogate; that does not establish the former.

Three of the other 57 factory configurations were provably refused by original source before any audit edit:

- `baseline_symmem_training.py` and `optimized_symmem_training.py` pass `--allow-single-gpu`. Original `ch04/symmetric_memory_training_advanced.py:init_distributed` lines 105–106 raises whenever that flag is true. Its original CLI help explicitly calls this mode removed.
- `baseline_symmem_training_multigpu.py` passes `--disable-symmetric`. Original `main` lines 880–883 sets `SYMMETRIC_MEMORY_DISABLED`; `symmetric_memory_available` lines 98–99 returns false, and `init_distributed` lines 109–110 raises. More GPUs do not make this declared baseline configuration executable.

The remaining **54 non-ZeRO factories** point at existing DDP (8), compression (7), FSDP/FSDP2 (8), pipeline (22), ZeRO-1/3 (8), and optimized multi-GPU symmetric-memory (1) child paths. Their source contains implementations or dispatchers and conditional hardware/dependency guards. The bounded review does not establish any of these 54 as universally unexecutable, nor does it prove them correct or supported on a particular stack. The original README advertised harness execution, and old expectations contain timing records; those records are historical claims, not valid child-correctness evidence.

Within ZeRO's four, original `optimized_zero2.py` already had the nonexistent-hook refusal described by W1-091. Original `optimized_zero2_multigpu.py` had an executable loop with the W1-004 no-update defect, rather than a guaranteed launch refusal. Both baselines had training implementations, with parity defects subsequently repaired under LOCAL-006. Thus `3 pre-existing explicit refusals + 54 other paths + 4 ZeRO paths = 61`; the inventory preserves exact names and arguments.

This does not authorize restoring removed symmetric-memory fallback/single-GPU features, restoring arbitrary backends, or certifying the other 54. Keep their current non-acceptance explicit and decide restoration by actual workload contract. Do not dismiss all 57 as pre-existing unsupported features or close LOCAL-019's remaining functional gap by counting refusal tests.

## Smallest useful next source slice

Implement **one ZeRO-specific actual-child result adapter**, shared by the four existing ZeRO factories, while leaving the generic wrapper's unsupported default intact. The source seam is `zero2_common.py` (child results), a narrowly scoped ZeRO adapter/protocol module, the four factory return types, and the minimum harness/verification transport hook needed to consume those results. `zero2.py` remains the real dispatcher. Shared harness paths require explicit ownership coordination before edits.

1. Resolve one workload specification from the real factory/config/extra arguments: world size, model dimensions, seed, precision, accumulation, AdamW options, clipping, warmup, steps and optional payload. Use the actual values, not label hashes. Keep baseline/optimized workload equality. Refuse unsupported combinations explicitly. A smaller validation workload is a separately labeled case, never qualification of a larger timed workload.
2. Have the actual `zero2_common.run_training` child produce full numerical results, not just stdout: initial and updated parameters, gradients, optimizer moments/step counts, losses and actual rank inputs or an exact replayable input stream, with every expected rank and more than one update. Include warmup's state change. Save rank artifacts atomically to a fresh parent-owned attempt directory; preserve artifacts and failures. Provenance IDs/hashes bind a run but cannot prove numerical correctness. Avoid arbitrary pickle loading, path traversal and stale/replayed artifacts.
3. Compare those actual child tensors with an independent dense mathematical reference using the same initial parameters and every rank's actual microbatches: world-average gradients, accumulation, clipping and AdamW. The reference must not call the candidate communication hook or `training_step`, must not merely compare two identically broken candidates, and must not substitute a parent toy model. Require actual parameter changes, optimizer step/state progression, full replica equality and correct sharded state ownership. Use justified numerical budgets; do not invent GPU calibration from CPU results.
4. Make the real harness path consume and validate that result contract before accepting a benchmark row. Missing/duplicate rank, missing output/state, no update, changed last element, nonfinite output, unrelated successful child, child error, timeout and stale run must reject. A successful child exit, model identity digest, nonempty log, or stdout throughput value is not correctness evidence. No `skip_output_verification`, fabricated cached payload, lowered threshold or generic fallback should bypass the adapter.
5. Preserve measurement scope. Reference evaluation, artifact serialization and validation belong outside the measured training interval; explicitly distinguish process-wall time from child training time. Never turn summary timing into raw per-step samples. If complete payload capture or reference checking adds work to process-wall time, label it rather than reporting an unchanged throughput claim. Validate the same workload that is timed before accepting its performance; resource limits produce HOLD, not silent resizing or partial tensors.

Start with real CPU/Gloo child-process positive and negative transport/update checks, using an explicitly labeled CPU validation mode if needed; do not pretend CUDA exists or bypass GPU gates. Then run the existing four factory/dispatcher combinations through the public harness on actual allocated one-/two-GPU targets with pinned CUDA/NCCL, retaining full rank artifacts and an independent reference. Keep CUDA, default-scale/12-GiB payload, compilation, performance and memory claims pending until their exact cases run. A source-only adapter can advance implementation; it cannot finish target qualification.

Recommended status wording: **“False parent verification withdrawn; ZeRO child-result integration required; generic workload verification remains unsupported pending per-workload contracts.”** Keep W1-004/W1-091's repaired optimizer source and prior CPU receipts intact, but add their harness integration dependency to remaining acceptance. The wider user goal remains open; no finding or permission is silently removed by this review.
