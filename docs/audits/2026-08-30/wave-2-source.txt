code/ch12/cuda_extensions/cuda_graphs_kernels.cu:99
Cached CUDA graph replays a stale baked data pointer; optimized benchmark never touches its tensor
critical
ch12–14 graphs/compile/FP8
verified by independent skeptic
Problem
graph_replay() captures kernels with `data.data_ptr<float>()` baked in, but the cache-rebuild check keys only on (device, num_elements, iterations) — NOT on the data pointer. optimized_cuda_graphs.py setup() captures during warmup (line 45: `self._extension.graph_replay(self.data, self.iterations)`) and then REPLACES the tensor (line 49: `self.data = torch.linspace(...)` — the RHS allocates a new buffer while the old one is still alive, so the address is guaranteed different). Every subsequent timed benchmark_fn() call hits the cache and replays the graph bound to the FREED original allocation, which the caching allocator typically hands to `self._verify_input`/`_verify_output_buffer` next — so the replay silently corrupts the verification input while `self.data` stays a pristine linspace. The 'optimized' result is a replay writing garbage into a repurposed buffer, and the captured verification output is the untransformed input (baseline converges to ~0.105 everywhere; optimized reports linspace 0..1). optimized_cuda_graphs_router.py has the identical pattern (warmup capture line 41, reassignment line 45). The sibling extension graph_bandwidth_kernels.cu (lines 105-106) keys its cache on dst_ptr/src_ptr, showing this is an omission, not a design choice.

Evidence
cuda_graphs_kernels.cu lines 99-102: `bool needs_capture = (g_graph_cache.exec == nullptr) || (g_graph_cache.device != device_id) || (g_graph_cache.num_elements != n) || (g_graph_cache.iterations != iterations);` with line 114 baking `data.data_ptr<float>()` into the captured launch; optimized_cuda_graphs.py line 45 `self._extension.graph_replay(self.data, self.iterations)` followed by line 49 `self.data = torch.linspace(0.0, 1.0, self.N, dtype=torch.float32, device=self.device)`.
Suggested fix
Add `const float* data_ptr` to GraphCache and include `g_graph_cache.data_ptr != data.data_ptr<float>()` in needs_capture (as graph_bandwidth_kernels.cu already does), or update the exec's kernel node params via cudaGraphExecKernelNodeSetParams when the pointer changes. In the Python wrappers, stop re-allocating self.data after the capture warmup — reset values in place with `self.data.copy_(...)`.

Verifier notes
needs_capture (lines 99-102) keys only on exec/device/num_elements/iterations — no data pointer — while lines 114-116 bake data.data_ptr<float>() into the capture. optimized_cuda_graphs.py setup() captures at line 45 then reassigns self.data at line 49; the old tensor is still referenced during the torch.linspace allocation, so the new address is guaranteed different, and every timed benchmark_fn (line 56) replays the graph bound to the freed original buffer (likely reused by _verify_input/_verify_output_buffer allocated at lines 50-51). self.data is never modified by the replay, so the captured 'output' is the untransformed linspace, masked by the loose (0.1, 1.0) tolerance at line 75. optimized_cuda_graphs_router.py has the identical pattern (capture line 41, reassignment line 45). graph_bandwidth_kernels.cu keys its cache on dst_ptr/src_ptr (lines 105-106, 150-151), confirming this is an omission. Critical is correct: the optimized measurement is invalid and it silently corrupts a repurposed allocation.

code/ch12/optimized_graph_conditional_runtime.cu:282
Conditional WHILE graph never terminates and its body is never populated (phGraph_out is an output parameter)
critical
ch12–14 graphs/compile/FP8
verified by independent skeptic
Problem
The code builds a WHILE-type conditional node and passes its own populated body graph via `phGraph_out`. In the CUDA API, `conditional.phGraph_out` is an OUTPUT array: cudaGraphAddNode writes the handle of a newly created, EMPTY body graph into it. So the `while_body` that received `expensive_kernel` (line 257) is discarded (the variable is overwritten with the node-owned empty graph), and the conditional body is never populated. Worse, the WHILE condition handle is set to 1 by `set_condition_kernel` (data mean ~1.5 > threshold 0.5) and nothing inside the body ever calls cudaGraphSetConditional(handle, 0), so the WHILE node re-evaluates a permanently non-zero handle and loops forever. On any CUDA 12.4+ machine the very first warmup `cudaGraphLaunch` (line ~302) spins the GPU indefinitely and `cudaStreamSynchronize(stream)` never returns — the 'optimized' benchmark hangs and the expensive kernel it claims to measure is not even in the graph. The comment at line 261 ('WHILE with initial value 1 runs once if we don't loop') states semantics that do not exist. The ch12 Makefile auto-builds every *.cu, so this broken binary is a shipped target.

Evidence
Line 257: `CUDA_CHECK(cudaGraphAddKernelNode(&expensive_node, while_body, nullptr, 0, &expensive_params));`  Line 261: `// WHILE with initial value 1 runs once if we don't loop`  Lines 281-282: `cudaGraph_t* body_graph_ptr = &while_body;` / `while_params.conditional.phGraph_out = body_graph_ptr;`  Line 286: `CUDA_CHECK(cudaGraphAddNode(&while_node, graph, while_deps, nullptr, 1, &while_params));` — body graph handed in before cudaGraphAddNode, no cudaGraphSetConditional(handle, 0) anywhere in the body.
Suggested fix
Create the conditional node first with an empty `cudaGraph_t body; while_params.conditional.phGraph_out = &body;`, then add `expensive_kernel` (plus a tail kernel that calls `cudaGraphSetConditional(handle, 0)` to give IF-like run-once semantics) into the RETURNED `body` graph before instantiation. Alternatively use `cudaGraphCondTypeIf`, whose body runs at most once per launch, and populate the returned body graph the same way.

Verifier notes
Evidence matches: line 257 adds expensive_kernel to while_body; lines 281-282 set while_params.conditional.phGraph_out=&while_body BEFORE cudaGraphAddNode (line 286). Per NVIDIA docs, phGraph_out is populated BY cudaGraphAddNode with a CUDA-owned empty body graph — a caller-populated graph passed there is never installed as the body, so expensive_kernel is not in the executed graph. The handle is set to 1 by set_condition_kernel (initial data 1.0+(i%100)*0.01, mean ~1.495 > threshold 0.5) and no kernel in the (empty) body calls cudaGraphSetConditional(handle,0), so the WHILE re-evaluates a permanently nonzero handle: the first warmup cudaGraphLaunch (line 301) loops forever and cudaStreamSynchronize (line 303) never returns. Line 261 comment claims run-once semantics WHILE nodes do not have. ch12 Makefile confirms 'Auto-builds all *.cu files' via wildcard, so this hanging binary is a shipped target. Critical is correct.

code/labs/custom_vs_cublas/cutlass_gemm/cutlass_gemm.cu:125
stride_B built from swapped (K,N) shape; wrong results for any K != N
critical
Tail pass
hand-verified by session lead
Problem
CUTLASS 3.x convention passes B's shape as (N, K, L) regardless of layout tag -- the StrideB type (TagToStrideB_t<ColumnMajor> = Stride<int64_t, _1, int64_t>) already encodes the layout, and make_cute_packed_stride sets the dynamic N-mode stride to shape[1]. Passing {k, n, 1} makes B's N-mode stride N instead of K, so for any non-square GEMM (K != N) the kernel reads B at wrong offsets (wrong numerical results and potential out-of-bounds reads). It only accidentally works for square problems. Every other CUTLASS GEMM in this repo (labs/nvfp4_gemm/*.cu, ch09/*.cu) correctly uses {n, k, 1}. [Hand-verified by session lead: all five sibling GEMM files pass {n, k, 1}.]

Evidence
StrideB stride_B = cutlass::make_cute_packed_stride(StrideB{}, {k, n, 1});  // (K,N) for ColumnMajor
Suggested fix
Change to `StrideB stride_B = cutlass::make_cute_packed_stride(StrideB{}, {n, k, 1});` (and drop the misleading comment); B is an (N,K) tensor whose N-mode stride must be K.

code/ch09/baseline_cublas_gemm_fp4_perchannel.cu — B operand quantized/packed along N instead of K, so cuBLASLt consumes B-transposed with scale blocks on the wrong axis (wave 2)

The central numerical claim does not hold. layoutB (kK,kN,ld=kK, default col-major, line 201) over the row-major KxN packed buffer makes cuBLASLt consume L_B(k,n)=B[n][k]: consecutive memory IS consecutive k of the consumed operand, so the operand is K-major as NVFP4 requires, and each quantizer block (16 contiguous N-elements of B row n, line 77) is exactly one 16-element K-block of the consumed operand for output column n, with its scale at the plain [n][kblock] index (line 81) - the scale blocks are on the CORRECT axis of the operand the hardware actually reduces over. The only true residue is that the GEMM computes A@B^T of i.i.d. random data instead of A@B; the file states no reference product, performs no reference verification, and the checksum pair is self-consistent, so this is a labeling nuance, not a correctness defect.
